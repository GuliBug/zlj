# 前端设计（frontend）

## Context

- 需求上游（PRD v1.8）与 4 个配套交付件（H5 原型 / Web 管理端原型 / 时序图与流程图 / 需求总览）原先存放于仓库外路径 `D:/projects/zlj/需求/`，该目录在当前开发机不存在。
- 主规格 `H5买家端/frontend/spec.md` 的 **H5-11** 与 `管理端/frontend/spec.md` 的 **WA-18** 均以「原型文件绝对路径」作为结构基准（SHALL 条款），路径失效后该条款不可验证。
- `openspec/config.yaml`、`AGENTS.md`、`README.md` 三处声明的需求上游同样指向该失效路径。

本 change 不改任何前端代码，只处理需求资产的位置与引用。

## Goals / Non-Goals

**Goals**

- PRD v1.8 与配套交付件成为仓库内可追溯、可版本管理的稳定资产。
- 主规格中的原型基准路径在仓库内可解析，SHALL 条款可验证。
- 全局文档（config / AGENTS / README）声明的需求上游与主规格指向同一份文件，避免出现两份"权威需求"。

**Non-Goals**

- 不修改 PRD 正文任何字符（版本号、章节结构、FR 编号、状态机、枚举值一律不动）。
- 不新增、删除、重命名 OpenSpec 能力目录，不调整主规格库的目录结构。
- 不改动前端工程（frontend-h5 / frontend-web）任何源码、依赖、构建配置。

## Decisions

### FD1：需求资产采用「稳定基线库 + change 输入快照」双层存放

- **方案**：PRD 与配套交付件存放于 `docs/需求/`（稳定基线库）；同时在本 change 的 `prd/` 目录下保留 PRD 单文件副本，作为本次变更的输入快照。
- **理由**：
  - `prd/` 随 change 生命周期移动（归档时进入 `openspec/changes/archive/2026-11-05-202611-需求基线-v1.8/`），路径会变。若主规格与全局文档直接引用 change 内路径，**归档动作本身就会让引用失效**。
  - 因此凡是被「跨 change、跨时间」引用的需求资产，必须放在路径稳定的仓库级目录；`prd/` 只承担「本次变更的输入材料」语义。
- **取舍**：PRD 存在两份副本（`docs/需求/` 与 `prd/`）。接受这一冗余，换取引用路径的稳定性；两份内容逐字节一致，PRD 正文修订时需同步更新。

### FD2：引用一律使用仓库相对路径，不使用盘符绝对路径

- **方案**：`config.yaml`、`AGENTS.md`、`README.md`、主规格中的需求与原型引用，统一改为 `docs/需求/...` 形式的仓库相对路径。
- **理由**：绝对路径 `D:/projects/zlj/...` 绑定单台机器与单盘符，在其他成员机器、CI、容器中均不可解析，是本次断链的直接根因。
- **取舍**：仓库相对路径要求阅读者以仓库根为基准理解路径；相比绝对路径牺牲了「脱离仓库也能点开」的便利性，换取可移植性。

### FD3：仅修正路径，不动 requirement 的结构基准描述

- **方案**：H5-11 与 WA-18 采用 `MODIFIED` 整块复制，**只替换文件路径字符串**，其余结构基准描述（品牌导航、警示条、hero 与四宫格、分档 chips、TabBar 四项；侧栏 7 菜单、主色 #8f1d22 / #241d18、工作台指标卡、新增商品三步流程、门店页核销记录）与场景全部逐字保留。
- **理由**：需求基线入库是**位置变更**，不是结构变更。若趁机调整描述，delta 将掩盖真实变更范围，后续归档时主规格的差异无法归因。
- **取舍**：主规格中「原型是结构基准」这一强依赖被保留，意味着原型 HTML 一旦与实现漂移，仍需靠人工比对发现 —— 这属于现状的既有风险，本 change 不扩大也不解决。

### FD4：配套交付件一并入库

- **方案**：PRD 内文与仓库内其他文档直接引用了 4 个配套件（附录 A 引 H5/Web 原型、8.4 引时序图 HTML、总览引用 PRD 与三件），故 5 个文件整体入库 `docs/需求/`。
- **理由**：只入库 PRD 会让 PRD 自身的引用继续指向不存在的文件，等于把断链从仓库外搬进仓库内。
- **取舍**：`docs/需求/` 增加约 185 KB（其中 HTML 原型 108 KB），均为人可直接双击打开的无依赖单文件，价值高于体积成本。

## Risks / Trade-offs

- **[风险] PRD 双副本可能不同步**：`docs/需求/` 与 change 的 `prd/` 各存一份，后续修订 PRD 正文时若只改一处会产生分歧。
  → **缓解**：PRD 正文修订不在本 change 范围，需另行立项 change 并明确「同步更新两处」；归档前校对两份文件的哈希一致。

- **[风险] `docs/需求/` 下的 HTML 原型被误当作现网实现依据**：原型内含示例商品与门店数据。
  → **缓解**：PRD 附录 A 已声明「原型中商品名/门店/文案为参考示意」，且主规格明确「页面数据 SHALL 来自真实接口，不得硬编码原型的示例数据」，两者共同约束。
